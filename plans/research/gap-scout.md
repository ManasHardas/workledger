## Gaps found (ranked by evidence volume)

### GAP-1 — A recorded decision cannot be enforced, only recited
**Sources:** E-G12 (45 reactions, open 14 months), E-G13 (closed not_planned), E-G14, E-G15, E-G16, E-G17, E-G28 (≈112 hand-built decision hooks), E-G33 (zero products).
**Who has it:** every operator who writes rules down. The precise operator persona: E-G16 documented an architecture decision in `PROJECT_LOG.md` *and* the memory file, and the agent contradicted it in production three times in one session without flagging it.
**Structural or closes-on-contact:** **structural, and the strongest on the board.** Anthropic has now closed this ask twice as `not_planned` (E-G13, E-G17) and once let it die by inactivity bot. A harness vendor cannot ship "we will mechanically block the model from violating your written decision" without publishing an admission that its model does not follow instructions — the ask *is* the bug report. Worse, enforcement must live at the tool boundary (PreToolUse exit-2, CI), which is architecturally outside the model, i.e. exactly where a third party is allowed to sit.
**Existing workaround:** PreToolUse hook farms — E-G14's 24-hook compliance system, `npx cc-safe-setup`, CRE, and the ≈112 in-repo `.claude/hooks` files with decision/ADR/spec names. Critically, **every one of these enforces generic safety rules** (`rm -rf`, push-to-main, editing test files). None enforces a *project-specific recorded decision*. arwoxb24's own limit statement: hooks "cannot prevent the model from generating wrong intent — the hook catches it after generation."

### GAP-2 — No promotion boundary: an agent inference silently becomes team truth
**Sources:** E-G7, E-G8, E-G9, E-G25, E-G26 (four fleets), E-G22 (mem0 closed it not_planned), E-G31 ("memories become incorrect" is the #3 breakage).
**Who has it:** anyone whose memory store is written by agents and read by other people's agents. The #38536 thread converged on this independently of the original request.
**Structural:** **mostly structural.** mem0's maintainer stated ADD-only + linked memories is *intended design* (E-G22) — approval is one low-volume write against a business metered on ingestion and retrieval. Warp/Copilot-class auto-capture vendors sell "you don't have to do anything"; a promotion gate reintroduces the work they sell the absence of.
**Workaround:** the two-writer RBAC design in E-G9, `memory-tombstones` ledgers (E-G26), Total Recall's "write gates" (E-G29), and simon9679's external read-only auditor bolted onto mem0 (E-G22).

### GAP-3 — Negative knowledge has no home
**Sources:** E-G10 (900 records, zero decisions — activity capture records commands, not reasoning), E-G27 (`bdx-outcome`: "record success/failure + approach when closing" — hand-built, closed not_planned), E-G32 (Copilot re-reviews "repeat the same incorrect suggestions"), E-G6 ("what was tried, what failed"), E-G25 ("no way for a task to cite the exact knowledge it used").
**Who has it:** everyone; almost nobody articulates it as a request. This is the gap with the **highest strategic value and the lowest explicit demand** — it appears as symptom ("it re-tried the thing we abandoned"), never as feature request.
**Structural:** **structural for a boring reason** — abandoned work produces no commit, no PR, no green CI. Every capture layer that keys on artifacts (Entire on commits, Copilot on code citations, claude-mem on PostToolUse tool calls) is structurally blind to it. E-G10 is the clean proof: the pipeline faithfully recorded what it was pointed at, and it was pointed at bash commands.
**Workaround:** hand-written notes outside the store (E-G10 explicitly), tombstone ledgers (E-G26).

### GAP-4 — You cannot correct a memory, and correction is not the same as deletion
**Sources:** E-G22, E-G23 (Graphiti #934 open ~12 months), E-G24 (cognee: hackathon only), E-G25 ("a corrected policy can silently replace the only copy of the old policy"), E-G26 (bee-ghosttrack's retire-to-tombstone rule; timsehn 2026-08-22: agents are "very 'precious' with memories … really reluctant to delete"), E-G21 (97.8% junk, 186/224 survivors had to be rewritten).
**Structural:** **partly** — supersession-with-history is cheap to build and Notion Lore and Sentra already ship it (per research-thirdparty). The durable half is that a correction must carry *who corrected it and on what authority*, which is GAP-2 again.
**Workaround:** external auditors, tombstone ledgers, periodic manual purges.

### GAP-5 — Team/org scope, asked constantly, granted nowhere in OSS
**Sources:** E-G3 (three team-DB requests, all closed), E-G4/E-G11 (nine competing builds under one open issue), E-G18, E-G30 (skeledrew asks for cross-project), E-G31 ("tools don't share brains").
**Structural:** **weakly — this closes on contact.** Warp and Copilot Memory already cross the boundary in some form; the whole of E-G11 is people shipping it this year. Do not build for this alone.

### GAP-6 — Org-wide active-work awareness
**Sources:** E-G5, E-G20, E-G19.
**Structural:** **no — it is closing now.** #24798 (21 reactions, 84 comments) shipped as **completed** on 2026-08-17. Presence requires a registry the harness owns.

## Which gaps map to the operator's two stated pains

**Pain 1, "re-briefing a new session."** Maps to GAP-5 and GAP-6, plus handoff (E-G18). This is the operator's *loudest* pain and the **worst** commercial position in this report: three closed team-DB requests (E-G3), nine competitors under one issue (E-G11), a shipped first-party inter-session channel (E-G19), and a forum consensus that a plain markdown file already wins (E-G31). Serve it as a by-product, never as the pitch.

**Pain 2, "decisions forgotten or violated."** Maps to GAP-1 + GAP-2 + GAP-3 + GAP-4 — and every one of those four is either closed-as-not-planned by the incumbent or open-and-rotting. E-G16 is the operator's exact incident, filed by a stranger, and closed `not_planned`. Note the asymmetry: the operator names *violation* ("agents redoing/undoing/contradicting settled decisions"), and violation is an **enforcement** problem, not a memory problem. A record that is retrieved and then ignored (E-G12, E-G15, E-G17) has not solved pain 2.

## The single gap with the strongest combination of evidence volume and structural durability

**GAP-1 fused with GAP-2: a decision record whose promotion is human-gated and whose violation is mechanically blocked.**

Evidence volume: E-G12's 45 reactions is the largest single-issue signal found anywhere in this scout, and it has been open since 2025-06-24. Three further asks (E-G13, E-G15, E-G17) were closed `not_planned` — a decline, not an absence of demand. The hand-rolled workaround is at industrial scale (E-G28), and it is already *hook-shaped*: `decision-nudge.js`, `decision-trace-capture.sh`, `adr-trigger-infra-changes.txt`, `spec-guard.sh` are people building this product badly, one repo at a time.

Structural durability: (a) the incumbent has to say no, because "block our model from violating your rule" is a self-indictment, and it has said no three times; (b) enforcement lives at the tool/CI boundary that is outside the model and open to third parties; (c) memory vendors are metered on write and retrieval volume, so a low-volume approval event plus a *blocking* gate is anti-revenue for all of them (mem0 stated the ADD-only design is intentional, E-G22); (d) E-G33 — nobody sells ADR enforcement at all, and the one repo that tries has zero stars.

The product sentence this implies is **not** "give agents memory." It is: *the decision the human approved is the one the agent is not permitted to violate, and the violation attempt is logged with what was tried and rejected.* GAP-3 then falls out for free — a blocked attempt **is** a negative-knowledge record, captured at the one moment it exists, which is the only known answer to E-G10's 900-records-zero-decisions problem.

## Negative results

- **claude-mem's issue tracker does not support the thesis.** 325 open issues, top open-issue reaction count 3, and the entire top-40 is reliability and packaging (E-G2). Every team-memory request is closed (E-G3). A 93k-star memory tool's users are asking for it to *work*, not for it to become governed. Anyone citing claude-mem's star count as demand for org memory is citing the wrong number.
- **Cursor's forum has essentially no Memories complaint corpus.** Only two low-engagement topics surfaced (155187, 1 post; 167695, 2 posts); the substantive thread (159891) is about markdown files across tools, not about Cursor Memories (E-G31). Consistent with research-native's finding that Cursor ships no documented Memories feature.
- **GitHub Copilot Memory complaints were not found.** Four GraphQL discussion searches over `community/community` for wrong/org-wide/cross-repo memory returned only billing and unrelated threads; the closest hit is #190754 about code-review amnesia (E-G32). Either Copilot Memory is working, or its feedback is not public. **Do not claim Copilot Memory users are unhappy.**

- **Warp community was not reached** — no accessible forum endpoint was found without a search budget. Warp Agent Memory complaints remain unmeasured.
- **"Show HN" traction in this category is real but thin and getting thinner per entrant**: OKF Agent Memory 74 pts (E-G30), Total Recall 67 pts (E-G29), and a long tail of 1–5 point memory launches. The two that broke 60 both led with a *constraint* — "write-gated", "git-native" — not with "memory".
